ตารางและเกณฑ์ในเอกสารนี้สร้างจากโค้ดของระบบโดยตรง (tools/build_measurement_doc.py)

1. วัตถุประสงค์และหลักการ

เอกสารนี้อธิบายว่าระบบตัดสิน ระดับความรุนแรง ของ finding, ความน่าเชื่อถือ ของ finding, finding ใดต้อง เข้า workflow, การวัด MTTC และการ จัดอันดับความเสี่ยง อย่างไร

หลักการ: ทุกระดับที่ระบบแสดงต้องอธิบายได้ว่า อ้างอิงมาตรฐานใด และ ตัดสินจากข้อเท็จจริงใด ในประโยคเดียว ขั้นใดที่ไม่มีมาตรฐานรองรับโดยตรง จะระบุชัดว่าเป็น "วิธีภายใน" พร้อม framework ที่ใกล้ที่สุด

ลำดับการทำงาน: log ที่อัปโหลด → แปลงเป็นข้อมูลกลาง → detection rule สร้าง finding → กำหนดระดับพื้นฐานตาม Sigma → ปรับตามผลของ firewall → ยกระดับตาม attack path → ให้คะแนนความน่าเชื่อถือ (Admiralty) → finding ระดับ high ขึ้นไปเข้า workflow

2. ความรุนแรง (Severity)

2.1 ระดับพื้นฐาน: Sigma rule level

อ้างอิง Sigma rules specification v2.1.0 (field level) ทุก detection rule ประกาศระดับของตัวเอง โดยพิจารณาว่า พฤติกรรมนั้นเพียงลำพัง ตรงกับนิยามใดของ Sigma ระบบเลิกใช้สเกล 0-15 แบบเดิมที่ไม่มีมาตรฐานรองรับแล้ว

ระดับน้ำหนักนิยามตาม Sigma (สรุป)
ข้อมูลประกอบ (informational)1ใช้ติดป้าย/เสริมข้อมูลเหตุการณ์ ไม่ควรเปิดเคสหรือแจ้งเตือน
ต่ำ (low)2เหตุการณ์ที่น่าสังเกตแต่ไม่ค่อยเป็น incident มีความหมายเมื่อเกิดจำนวนมากหรือร่วมกับเหตุการณ์อื่น
ปานกลาง (medium)4เหตุการณ์ที่เกี่ยวข้อง ควรตรวจสอบด้วยคนเป็นประจำ
สูง (high)8ควรแจ้งเตือนภายในและต้องตรวจสอบโดยเร็ว
วิกฤต (critical)16บ่งชี้ว่าเป็น incident ต้องตรวจสอบทันที ใช้เมื่อความน่าจะเป็นเกือบแน่นอน

น้ำหนักเพิ่มเป็นสองเท่าต่อระดับ ใช้สำหรับ เรียงลำดับและคำนวณคะแนนความเสี่ยงเท่านั้น ป้ายที่แสดงให้ผู้ใช้เห็นคือชื่อระดับเสมอ

ไม่มี rule เดี่ยวตัวใดได้ระดับ critical เพราะ Sigma สงวน critical ไว้สำหรับกรณีที่ความน่าจะเป็น "เกือบแน่นอน" ซึ่งเหตุการณ์เดียวใน log แทบไม่เคยถึง ระดับ critical จึงมาจากการยกระดับตาม attack path (ข้อ 2.3) เท่านั้น ปัจจุบันมี rule ระดับ high 20 ตัว, medium 18 ตัว, low 6 ตัว, informational 0 ตัว

2.2 การจำกัดระดับเมื่อ firewall ปฏิเสธ

แถวที่ firewall บล็อก (deny, drop, reject, reset ฯลฯ) จะมีระดับ ไม่เกิน medium ไม่ว่าจะเป็น rule ใด อ้างอิง ODNI Cyber Threat Framework ซึ่งแบ่งการโจมตีเป็น Preparation → Engagement → Presence → Effect และกำหนด "เส้นการบุกรุก" ไว้ระหว่าง Engagement กับ Presence ความพยายามที่ถูกบล็อกยังไม่ข้ามเส้นนี้ ตัวอย่างเช่น beacon ไปยัง C2 ที่ถูกบล็อกทุกครั้งเป็นเพียงความพยายาม ยังไม่ใช่ช่องทางที่ติดต่อได้จริง

2.3 การยกระดับตาม attack path

เมื่อหลักฐานใน path เดียวกันแสดงว่าการโจมตีข้ามเส้นการบุกรุกแล้ว finding บน path นั้นจะถูกยกระดับ แต่ละรูปแบบเป็นประโยคที่ analyst ตรวจสอบกับข้อมูลได้ และหน้าจอแสดง rule ที่เป็นหลักฐานกำกับไว้

รูปแบบยกเป็นเงื่อนไข
credential-compromisehighต้นทางเดียวกัน brute-force บัญชีหนึ่ง แล้วตามด้วยการ login สำเร็จเข้าบัญชีนั้น
compromised-hostcriticalhost เดียวกันแสดงพฤติกรรมหลังบุกรุกตั้งแต่ 2 แบบที่ต่างกัน และ firewall อนุญาต
  • credential-compromise: ต้องมี brute-force (R2000 คือ fail ≥ 3 ครั้ง) จาก ต้นทางเดียวกัน แล้วตามด้วยการ login สำเร็จใน บัญชีเดียวกัน จากต้นทางนั้น จึงได้แค่ high ไม่ถึง critical เพราะ log แยกไม่ออกว่าผู้โจมตีเดารหัสถูก หรือเจ้าของบัญชีพิมพ์ผิดหลายครั้งแล้วเข้าได้
  • compromised-host: host เดียวกันแสดงพฤติกรรมหลังบุกรุก 2 แบบที่ต่างกัน ซึ่ง firewall อนุญาต ได้แก่ beaconing (R2007), traffic ไปยัง IP อันตรายที่ถูกอนุญาต (R3003), traffic ประเภท malware ที่ถูกอนุญาต (R3002) และการส่งข้อมูลออกขนาดใหญ่ (R3001) แต่ละพฤติกรรมเพียงอย่างเดียวยังมีคำอธิบายที่ไม่เป็นอันตรายได้ แต่สองพฤติกรรมที่เป็นอิสระต่อกันบน host เดียวกันไม่ใช่
บทเรียนจากการวัดจริง: เวอร์ชันแรกให้ credential-compromise เป็น critical และนับแค่การเป็นหนึ่งในแหล่งของ password spray ผลคือ host ที่พิมพ์รหัสผิด 2 ครั้งแล้วเข้าได้ใน 9 วินาที (เป็นการพิมพ์ผิดชัดเจน) ขึ้นเป็น critical จึงปรับเป็นเกณฑ์ปัจจุบัน

2.4 ระดับของเคส

ระดับของเคสคือระดับสูงสุดของ finding ในเคสนั้น ถ้า event เดียวตรงกับหลาย rule จะใช้ระดับที่สูงที่สุด เคสที่มีแต่ finding ระดับ informational จะแสดงเป็น "None" เพราะ Sigma นิยามระดับนี้ว่าไม่ควรแจ้งเตือน

3. ความน่าเชื่อถือ (Confidence): Admiralty Code

อ้างอิง Admiralty Code (ระบบ 6×6 ของ NATO) ซึ่งให้คะแนน 2 แกนแยกกัน และเขียนรวมเป็นรหัส เช่น B2 ถ้อยคำของแต่ละระดับใช้ตามสเกลที่เผยแพร่ ส่วน ข้อเท็จจริงใดได้ระดับใด เป็นเกณฑ์ของระบบที่ระบุไว้ด้านล่าง

ความน่าเชื่อถือของแหล่ง (A-F)ความน่าเชื่อของข้อมูล (1-6)
ACompletely reliable1Confirmed by other sources
BUsually reliable2Probably true
CFairly reliable3Possibly true
DNot usually reliable4Doubtful
EUnreliable5Improbable
FReliability cannot be judged6Truth cannot be judged

3.1 ตัวอักษร: ความน่าเชื่อถือของแหล่ง log ตามที่ระบบอ่าน

  • A ไม่ให้เลย เพราะตัวอ่าน log ไม่สามารถอ้างได้ว่า "ไม่มีข้อสงสัยใด ๆ"
  • B อ่านคอลัมน์ตามเอกสารของ log source และไฟล์มี hash ที่บันทึกตอนรับเข้า ซึ่ง verify ผ่านทุกครั้ง
  • C อ่านตามเอกสาร แต่ hash บันทึกย้อนหลังหรือไม่มี hash หรือมีบาง field ที่ต้องเดา
  • D คอลัมน์ถูกเดาจากชื่อ ไม่ได้อ่านตามเอกสาร
  • E ไฟล์ไม่ผ่านการตรวจ hash ครั้งล่าสุด
  • F เคสเก่าที่ไม่มีบันทึกว่าอ่านไฟล์อย่างไร

3.2 ตัวเลข: ความน่าเชื่อของ finding

  • 1 entity เดียวกันปรากฏใน log source อื่น ของเคสเดียวกัน ซึ่งถือเป็นแหล่งอิสระตามความหมายของ Admiralty
  • 2 มี rule ≥ 2 กลุ่ม (R1 auth / R2 correlation / R3 network) และมี event สนับสนุน ≥ 5 ครั้ง
  • 3 มี rule กลุ่มเดียว หรือมี event น้อยกว่า 5 ครั้ง
  • 4 ไม่มี timestamp ที่ parse ได้ หรือ rule ยังเป็น experimental (ยังไม่เคยพิสูจน์กับข้อมูลจริง)
  • 5, 6 ระบบไม่ให้อัตโนมัติ: การปฏิเสธ finding เป็นหน้าที่ของ analyst ผ่านการ review

ป้าย high / medium / low ตาม section 6 ของสเปกยังใช้อยู่ โดยคำนวณจากตัวเลข: 1-2 = high, 3 = medium, 4-6 = low เมื่อ export เป็น STIX 2.1 ตัวเลขนี้แปลงเป็นค่า confidence ตามตารางของ STIX (1 = 90, 2 = 70, 3 = 50, 4 = 30, 5 = 10 และ 6 ไม่ระบุค่า)

4. เกณฑ์เข้า workflow, lifecycle และ MTTC

finding ที่เข้า workflow คือ finding ระดับ high และ critical ซึ่ง Sigma นิยามว่า "ควรแจ้งเตือนและตรวจสอบโดยเร็ว" finding ระดับต่ำกว่ายังแสดงในเคส แต่ไม่มีสถานะ workflow

สถานะNIST SP 800-61r3 / CSF 2.0
OpenRS.MA-02 (triage and validation)
InvestigatingRS.AN-03 (incident analysis)
ContainedRS.MI-01 (incidents are contained)
ResolvedRS.MI-02 (incidents are eradicated) / RS.MA-02 outcome
  • ก่อนเริ่ม investigate ต้องมีผู้รับผิดชอบ
  • สถานะ Contained ต้องบันทึกว่าดำเนินการ containment อะไรไปบ้าง
  • การปิด finding ต้อง review แล้ว และระบุ classification (true positive / benign true positive / false positive) พร้อมสรุป
  • true positive ต้องผ่าน Contained ก่อนปิด ส่วน benign TP และ FP ปิดจาก Investigating ได้ทันที
  • MTTC วัดจากเวลาที่ finding ถูกสร้าง (ครั้งแรกที่ rule engine ประมวลผลเคสเสร็จ) ถึงเวลาที่ถึง Contained และนับเฉพาะ true positive เพื่อไม่ให้ containment ที่ไม่ได้เกิดขึ้นจริงบิดเบือนตัวเลข

5. การจัดอันดับความเสี่ยงของ entity (วิธีภายใน)

ใช้ตอบคำถาม "ควรดูที่ไหนก่อน" ในเคสที่มี finding หลายพันรายการ

คะแนน = Σrule ที่เกี่ยวข้อง น้ำหนัก × (1 + ln n) โดยน้ำหนักมาจากระดับ Sigma และ n คือจำนวนแถวของ rule นั้นที่เกี่ยวกับ entity

แต่ละ rule นับเพียงพจน์เดียว และจำนวนครั้งถูกลดทอนด้วย log จึงวัดว่า "entity นี้เกี่ยวข้องกับการโจมตีกี่รูปแบบ" ไม่ใช่ "มี traffic มากแค่ไหน" ถ้าใช้ผลรวมธรรมดา host ที่ถูก scan และมี rule ที่มี noise มาก 3 ตัว จะได้อันดับสูงกว่าปลายทาง C2 ที่เป็นภัยจริง

ไม่มีมาตรฐานรองรับตรง: framework ที่ใกล้ที่สุดคือ NIST SP 800-30 (ความเสี่ยง = likelihood × impact) คะแนนนี้เป็นเพียงการเรียงลำดับฝั่ง likelihood เพราะการวัด impact ต้องรู้ความสำคัญของ asset ซึ่งระบบไม่มีข้อมูลนี้ คะแนนเป็นลำดับเท่านั้น ไม่ใช่ความน่าจะเป็น และนำไปเทียบข้ามเคสไม่ได้

7. ข้อจำกัด: สิ่งที่ระบบไม่ได้อ้าง

  • CISA NCISS: ระบบสอดคล้องกับ attribute "Observed Activity" แต่ไม่ได้คำนวณคะแนน NCISS เพราะต้องใช้ข้อมูลผลกระทบและการกู้คืน ซึ่ง log อย่างเดียวให้ไม่ได้
  • ODNI ↔ ATT&CK: ยังไม่พบเอกสารทางการที่จับคู่ทั้งสองไว้ การจับคู่เป็นของระบบเอง โดยยึดเส้นการบุกรุกที่ ODNI นิยามไว้
  • ไม่มี rule ใดเป็น stable ตามนิยามของ Sigma: ตอนนี้มี 21 ตัวเป็น test และ 23 ตัวเป็น experimental เพราะเพิ่งพิสูจน์กับข้อมูลของลูกค้ารายเดียว
  • ยังไม่มีรูปแบบ lateral movement เพราะใน corpus ไม่มีข้อมูลที่ใช้ปรับเกณฑ์ได้
  • เกณฑ์เข้า workflow (high ขึ้นไป) ต่างจากถ้อยคำใน FR-4.3 ("Critical หรือ ≥ 2 family") ซึ่งเขียนไว้สำหรับสเกล 0-15 แบบเดิม
